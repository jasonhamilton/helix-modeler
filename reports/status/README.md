**Summary:** The goal is a tool that listens to a recorded guitar tone and builds a matching preset for the HX Stomp pedal. The building blocks now work: the software can run both of its sound engines by itself, write preset files the pedal accepts, and check what it wrote. One real song has been taken through the whole chain by hand, and the owner found the result promising in an informal listen. What is missing is proof that the tool's own sense of what sounds similar can be trusted. On that song it could not tell its top two candidates apart, while the listener clearly preferred one. Until that judgement is validated, automatic matching cannot be relied on, and no blind listening test has been run. ### The tone comparison is not validated

**Critical** · Active Blocker

- **Problem.** The tool scores how close two guitar sounds are with several measures, and none has passed the required accuracy test on audio from the real Helix engines.
- **Impact.** The optimiser cannot be trusted to pick a genuinely matching preset, so [Gate 2](../../board/GATES.md#gate-2--recovers-known-presets-end-of-week-3 "Gate 2 — recovers known presets (end of week 3)") cannot be passed and automatic matching cannot be offered. On the one real song, the top two candidates scored 6.935 and 6.950 (lower is better), a gap too small to mean anything, while the listener clearly preferred one; the best score also swung from 7.7 to 22.7 depending on which clean guitar recording was used.
- **Cause.** Measures were built and checked on non-Helix stand-in signals, where the best one chose the right answer first only about 1 time in 8. Real Helix audio has not yet been tried because the known-answer set has not been rendered. The score also ignores loudness.
- **Resolution.** Render the known-answer set through Native, run the trust check on each measure, and combine or replace measures until the agreed accuracy is reached.
- **Owner.** benchmark and tone-metrics, with the lead freezing the thresholds
- **Next step.** Render the known-answer set through Native and run the trust check on it.
- **Evidence.** Tone-comparison trust check on stand-in signals; Informal listening to the first real-song matches; Known-answer set design and working targets

### The pedal and Native disagree on one cabinet setting

**High** · Confirmed Problem

- **Problem.** The cabinet's Early Reflections setting does not sound the same on the pedal and in Native.
- **Impact.** A preset found on the fast Native engine can sound different on the real pedal. At the value the search chose, the two engines' recordings cancel by only 3.6 dB (poor agreement); with the setting at 0 they cancel by 31 dB (close agreement).
- **Cause.** Not yet known. Candidates are an older algorithm in the pedal, a different parameter scale, or a delay-structure difference. Other parameters tested at their extremes agreed.
- **Resolution.** Find the cause, or measure every searchable parameter on both engines and let the search free only the parameters that agree.
- **Owner.** native-engine and stomp-engine; benchmark for the per-parameter audit
- **Next step.** Run the per-parameter agreement audit; until then any preset meant for the pedal keeps this setting at 0.
- **Evidence.** Pedal versus Native agreement on four presets; Decision log

### Guitar separation quality on real songs is unknown

**High** · Unknown/Unverified

- **Problem.** The step that isolates the guitar from a full mix has only been scored on an artificial mix. One real song was processed without a quality score.
- **Impact.** If the isolated guitar contains drums, vocals or artifacts, the tone comparison will chase those instead of the guitar and [Gate 3](../../board/GATES.md#gate-3--beats-the-nearest-preset-on-real-songs-end-of-week-4 "Gate 3 — beats the nearest preset on real songs (end of week 4)") results will be unreliable.
- **Cause.** No real-song stress set exists, and the only separation model aimed at guitar has no stated licence so it was not used.
- **Resolution.** Run the separation stress test on a few real songs, locally, and record how accuracy falls as the mix gets denser.
- **Owner.** separation, after the owner supplies songs
- **Next step.** Owner chooses the first songs (one action covers this and the [Gate 3](../../board/GATES.md#gate-3--beats-the-nearest-preset-on-real-songs-end-of-week-4 "Gate 3 — beats the nearest preset on real songs (end of week 4)") song set).
- **Evidence.** Separation run on the real song (no quality score)

### The library of measured blocks does not exist yet

**Medium** · Risk

- **Problem.** The per-block approach needs every effect block measured through Native, and the measuring kit has never been run on Helix.
- **Impact.** Choosing amp and effect models from measurements (instead of trying them blindly) is not possible, which makes the search space larger than it needs to be.
- **Cause.** The measuring kit was only finished offline on stand-in blocks. Native's current host is mono, so stereo blocks and dual cabinets cannot be measured; one unexplained accuracy floor remains when an amp follows other blocks.
- **Resolution.** Render the measuring signal through Native for a few blocks first, set tolerances from repeat-render spread, then capture the library overnight for mono blocks.
- **Owner.** native-engine, then benchmark and search
- **Next step.** Build the Native rendering of the measuring signal.
- **Evidence.** Block-by-block rendering test; Block measuring kit on non-Helix blocks

## Engines: what each can do and how fast

Times are in seconds (s), minutes (min) and hours (h). A render is one pass of a test signal through a preset, recorded as audio. A score is one comparison of a rendered candidate against the target tone (lower is better). A capture is the one-off step that teaches Helix Native a new chain, by loading the preset file into its editor and recording its state. A parity check renders one preset on both engines and compares the two recordings. Estimates are 100 times the newest measured time; every estimate says which measurement it uses and its date.

2. Native: the same render-pool speed-up (measured with 10 s clips) is assumed to hold for 2 s clips
3. Native: several engine hosts at once (a render pool), speed-up measured with 10 s clips
4. One after another: no parallel speed-up is measured for this activity (the benchmark steps run in sequence and a parity check needs the single pedal)
5. Native: only the renders run in parallel; scoring stays one after another
6. Native captures stay one at a time: capturing several chains in parallel is not measured yet

#### Helix Native engine

**Status:** working · **Health:** partial · **Evidence:** unit-tests, hardware

**Purpose.** Render a DI clip through a candidate preset offline in Helix Native, fast enough to be the searching engine.  
**Done when.** A NativeEngine behind the frozen interface renders any chain structure the search needs at a measured cost, loads candidates without a GUI step per candidate, agrees with the Stomp within a measured null residual, and has run a full synthetic recovery pass.  
**Functionality today.** Loads an arbitrary generated .hlx into Native with no human (in-process file drop, about 66 s per new chain structure, once per machine; needs TONEMATCH_NATIVE_AUTOCAPTURE=1 and a logged-in GUI session), drives parameters through a MIDI-CC map, and renders a 2 s clip in about 0.28 s with memory flat near 3.0 GB. Renders are history-independent and match each file's own capture at -317 dB. Mono in and out only; chains with an enabled delay or reverb need a 3 s pre-roll; Windows and Linux are untested.  
**Progress note.** Hands-off loading (file drop plus MIDI-CC map), state-based reset renders (0.28 s, bit-identical to dedicated captures at -317 dB, flat 3.0 GB), stale-template protection and a memory watchdog are built, hardware-measured on one Mac, and exercised by a 449-render real-song search. Block-serial rendering is shown to equal one instance above 20 Hz (-67 to -79 dB). Still missing: Windows and Linux (the drop route is macOS VST3 only), stereo and dual-cab paths in the host, a block-bypass CC encoding Native honours, the single-block library, and any full synthetic recovery pass. Quality of what Native renders versus the pedal is only partly in parity (see evaluation), and nothing it renders has been blind-tested by ear.

## Glossary

| Term | Meaning |
|---|---|
| blind A/B | A listening test where the listener does not know which option is which. |
| block | One element in a preset's chain: an amp, cabinet, drive pedal, delay and so on. |
| capture | The one-off step that teaches Helix Native a new chain: the preset file is loaded into its editor and the resulting state is recorded. |
| CMA-ES | An optimisation algorithm used to search for suitable settings. |
| dB | Decibel, a logarithmic loudness or level-difference scale. |
| DI | Direct Input: a clean, unprocessed guitar recording, before any amp or effects. |
| DSP | Digital Signal Processing: the audio calculations inside amps and effects. |
| Early Reflections | A cabinet setting that adds the first short echoes of the room. |
| EULA | The software licence agreement shown when installing a product. |
| firmware | The software running inside the pedal. |
| fw | Short for firmware, the pedal's built-in software. The pedal was on version 3.50 until 2026-10-15 and is now on 3.80. |
| gate | A milestone with a written checklist and a human sign-off. |
| held-out | Test items not used when tuning, so the result is not flattered by tuning. |
| Helix Native | Line 6's software version of the Helix sounds; it runs as a plugin and renders audio offline. |
| HX Edit | Line 6's editing program for the pedal; it also imports preset files. |
| HX Stomp | The Line 6 guitar-effects pedal this project targets. |
| known-answer set | A test set made by rendering presets we already know through Helix, so we can check whether the tool recovers them. |
| ledger | The project's append-only record of measured runs; a claim without a row did not happen. |
| loss | The score the optimiser tries to lower: how different two sounds are. Lower is a closer match. |
| MIDI CC | A control message that moves one knob or switch from software. |
